### Nuevo runtime: `.coferlandia/project-manager/projects.json`
```json
{
  "version": 1,
  "projects": [
    {
      "slug": "my-app",
      "path": "/abs/path/to/my-app",
      "added_at": "2026-07-13T12:00:00Z",
      "status": "active"
    }
  ]
}
```
- `slug`: identificador (default = basename del path).
- `path`: absoluto, puede vivir en cualquier parte del filesystem (ya no hay "carpeta compartida").
- `status`: `active` | `archived` (sacar sin perder historial).

## E. Onboarding + gestión de proyectos (requisito 2)

### Nuevo `scripts/pm-manage-projects.sh`
Primitivo no-interactivo, idempotente (testeable, sin `read` frágiles):
- `add <path> [--slug <slug>]` → valida que sea git repo, append a `projects.json` (crea el archivo si falta, desde template). Rechaza duplicados por path/slug.
- `remove <slug|path>` → marca `status: "archived"` (preserva historial).
- `list [--json]` → imprime proyectos activos.
- Flags globales: `--config <path>` (deriva `projects.json`), `--json`, `--help`.

### Extensión de `pm-onboard.sh`
Hoy: genera/valida `config.json` + doctor. Agrego:
1. Tras asegurar `config.json`, asegura `projects.json` (desde template si no existe).
2. Reporta `projects.json` status en el payload JSON (missing/empty/populated).
3. Si la lista está vacía, `next_approved_action` sugiere `add_first_project`.

El **loop interactivo "de a uno"** vive en **SKILL.md** (instrucciones al agente), no en el script: el skill le dice al agente que durante el onboarding pregunte al usuario por un path, ejecute `pm-manage-projects.sh add`, valide, repita hasta que el usuario diga "listo". Así el script queda componible y testeable, consistente con skills agent-driven.
